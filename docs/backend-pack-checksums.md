# Signed installed-file checksums

A backend index can add `files_blake3` to a pack entry. This optional map uses the same normalized relative paths as `files`, with 64 hexadecimal characters encoding the unkeyed 32-byte BLAKE3 digest of each complete installed file. Its key set must exactly equal the SHA-256 `files` key set. An empty, partial, extra or malformed map is rejected. Omission (or JSON null) retains legacy SHA-256 verification. Existing engines ignore the extension and continue checking `files`.

The index signature authenticates both maps. The artifact SHA-256 and artifact signature are unchanged. Installed receipts are not trust roots: discovery compares them with the signature-verified index, and validation compares the full expected manifest with the receipt. Editing a receipt cannot replace a signed digest or disable verification.

Installation verifies every SHA-256 digest and, when present, every BLAKE3 digest before publishing the installation. Index generation verifies both maps against extract archives before signing; install-time validation also covers bootstrap output. The Python generator needs `.github/requirements-backend-index.txt` when processing the extension. Integration packaging must compute the extension from the exact packaged bytes and carry it through its signed release catalog. An unsigned digest sidecar or a locally computed receipt is insufficient.

Each subsequent load reads and hashes every covered file with BLAKE3 when the authenticated complete map exists, otherwise SHA-256. Workers remain bounded at four, with one MiB buffers and the largest files first. This uses streaming BLAKE3 without Rayon or mmap. Metadata only schedules work. Missing files, read errors, worker failures and content mismatches fail validation; there is no fallback to SHA-256 after a BLAKE3 failure. Existing tree and symlink checks still run.

This extension does not introduce verification reuse, metadata caching, library loading before verification, or a new guarantee against mutation by a process with write access after verification. It retains the existing installation permissions and load path; supported-platform coverage and any stronger descriptor-to-loader binding remain separate work.

The September 19 A4000 diagnostic found streaming BLAKE3 reduced CUDA installed-file verification from about 371 ms to 228 ms. Those were isolated diagnostics, with SSH transfers active, not launch-to-model-ready qualification. The SHA-256 implementation comparison and the Rayon BLAKE3 variant were negative for CUDA and remain recorded. Startup must still pass the unchanged 1.5× gate with signed integration artifacts and the saved workload/configuration. No engine release or retirement of embedded ORT is authorized by this result.
